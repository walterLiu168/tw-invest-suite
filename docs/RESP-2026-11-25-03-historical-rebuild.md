## 0. 一句話

> ⚠️ **長樣本只能驗證「沒有 130% 出場規則」的版本。**
> 130% 融資維持率硬規則的資料來源 `finmind_taiwan_margin_maintenance`
> 只有 **2026-08-07 起**才有（151,174 列／74 個交易日／2,116 檔），
> 比帳本的回溯期短。任何跨 2026-08-07 的長樣本掃描，
> 測到的都是「規則完全不會觸發」的版本，不是 live 的那條規則。
> 在這段 70 個交易日的樣本裡，這條規則實際只關閉過 **AIV1 1 筆／H3 4 筆**交易：
> AIV1 有規則 −20.37% → 無規則 −21.28%（差 **+0.91pp**）；
> H3 有規則 −2.16% → 無規則 −1.84%（差 **−0.32pp**）。
> （第十一輪用正式引擎在 70 天母體上重測；舊的 −22.21%／+0.86pp、+0.16%／+0.55pp
> 是 57 天舊母體＋草稿模擬器的數字，已作廢。）
> → 結論：**長樣本不得推廣到含 130% 出場規則的版本**；
> 130% 條款的驗證範圍只有 2026-08-07 之後這一段。

重建**可行且已被證明忠實**（G1：2026-11-24 重建出 24/24，逐欄一致；
擴大到 2026-10-15、2026-11-05 三個日期仍逐欄 CLEAN，違例 0），
**G2 截斷對照已通過**（見第 3.1 節），
但**單日 156 秒**（原估）→ 2020–2026 約 1,660 個交易日需要約 **72 小時**單行程；
實測後改以 **4 個背景 shard** 並行，ETA 約 17～19 小時（見第 6.1 節）；
而且輸入資料有硬缺口（籌碼表只回溯到 2024-01-02、特徵表有空洞），
所以「能重建的日期範圍」需要先被界定清楚。

## 1. 為什麼不用 `scripts/market_screen_runner.py`

| 限制 | 位置 | 為什麼不行 |
|---|---|---|
| `--data-date` 必須等於最新資料日 | `market_screen_runner.py:519-525` | 直接擋掉歷史日期 |
| `persist_atomic()` 會把**更早**的 active picks 全部 CLOSE | `market_screen_runner.py:313-320` | 回填一個歷史日就會把今天那 24 檔關掉 → **G4 違規** |
| 需要 `metadata-backfill` 成功 marker | `market_screen_runner.py:553-556` | 歷史日期沒有 marker |
| 產物（MD／HTML／deep-dive）寫到共用的 REPORT_DIR | `generate_artifacts()` | 歷史批次會覆蓋今天的產物 |

→ 改寫成**離線重建**：呼叫同一支 `market_screen.screen_market()`，
把結果寫到 `scripts/_debug/_history_picks/<date>.json`（gitignored）。
**完全不碰 `market_screen_runs` / `market_screen_picks`** → G4 天然滿足。

## 3.1 G2 無前視檢查（✅ 通過）

方法：同一支 `market_screen.screen_market()`，對同一個目標日跑兩組——
**跑法 A（截斷組）** = `db.report_date(date)` context ＋ `db.latest_date` patch 到該日；
**跑法 B（不截斷組）** = 兩個開關都拿掉（讀到真實最新交易日）。
原始輸出：`scripts/_debug/_g2_truncation.json`（3 個日期各一筆完整快照）。

| 項目 | 結果 |
|---|---|
| 日期 | 2026-11-24／2026-10-15／2026-11-05 |
| 跑法 A vs DB 既有精選 | **全部 CLEAN**（ticker／horizon／bucket／score／e60／e240／rationale 全一致，違例 0） |
| 跑法 A vs 跑法 B：ticker 集合 | **不同** |
| 跑法 A vs 跑法 B：score | **不同** |
| 跑法 A vs 跑法 B：e60 | **不同** |
| 跑法 A vs 跑法 B：e240 | **不同** |
| 跑法 A vs 跑法 B：rationale | **不同** |
| 跑法 B 實際讀到的資料日 | **2026-11-25**（DB 最新資料日） |

三個日期的共同檔（common 8／5／6 檔）在 score、e60、e240、rationale 四個維度上
**每一檔都不同**（changed_count 全等於 common_count，沒有任何一檔相同）；
horizon 另有 2 個日期各差 1 檔（2026-11-24 為 0）。

**具體例（2026-11-05，1303）**：

| 欄位 | 跑法 A（截斷到 2026-11-05） | 跑法 B（不截斷） |
|---|---|---|
| score | 97.8405 | 96.6541 |
| e60 | +10.42% | −4.83%（翻正負） |
| e240 | 2.2046 | 1.7826 |
| zen 中樞區間 | 295.00 - 325.00（2026-10-20 ~ 2026-10-29） | 224.50 - 325.00（2026-10-29 ~ 2026-11-23） |
| 資料日 | 2026-11-05 | 2026-11-25 |

**判讀**：截斷機制確實在改變輸出，不是裝飾 → **重建語意成立**。

**殘餘風險（本次 G2 無法排除）**：`market_screen.screen_market()` 走的是日期綁定的
`db.all_latest_features(target_date)`／`db.all_latest_chipscore(target_date)`；
但 `scripts/db_client.py:193` 的 `ticker_features()`（讀 `stock_features` **最新一筆**，
`ORDER BY date DESC LIMIT 1`）與 `scripts/db_client.py:206` 的 `chip_features()`
（讀 `chipscore_daily` 最新 5 筆）**不是日期綁定** → 理論上仍有前視嫌疑
（目前這兩個函式在專案內無呼叫點，屬於潛在缺口而非現行路徑）。
A／B 兩組用的是同一份該資料，所以本次 G2 **無法區分這一維度**。

## 4. G1 的已知失敗模式（很重要）

G1 現在拆成三個子閘門，三者不可互相代替：

| 子閘門 | 問的問題 | 判定 |
|---|---|---|
| **G1-a**（樁） | 最新引擎重建近期日期，是否與 DB 既有精選**逐欄一致**？ | 2026-11-24／2026-10-15／2026-11-05 三個日期全部 CLEAN（24/24，違例 0） |
| **G1-b**（因子無前視） | 重疊檔的 e60／e240／rationale 是否一致（因子本身不含前視）？ | 三個 CLEAN 日期全部通過 |
| **G1-c**（選擇漂移） | ticker 差異能不能歸因到「引擎版本漂移」，而不是重建失敗？ | 逐日歸因見第 4.1 節；**漂移不得當成重建失敗** |

（下面這段屬於 G1-c：重建與「當時那個引擎」的輸入差異。）

`enforce_features=True`（live 排程用的路徑）會呼叫
`db.assert_feature_freshness(target_date, tickers, min_coverage=0.95)`，
而 `stock_features` 在 2026-08-12～08-19 期間**整段是空的**（0 列）→ 直接 raise：

```
stock_features freshness gate failed: date=missing expected=2026-08-12 rows=0/1943 coverage=0.0% required=95.0%
```

這代表：

1. **DB 裡那些日期的精選，本來就是在「特徵表沒有該日資料」的狀態下產生的**。
2. 重建要能重現它，就必須用 `--no-features`（不做特徵鮮度斷言），
   否則會在 2026-08 那一段全部失敗。
3. 更早的日期（例如 2024 以前）特徵表同樣稀疏 → 那些日期的重建是
   **「另一個輸入組合下的螢幕」**，不是「當時真正跑過的螢幕」。
   → 重建結果必須標註每個日期的輸入完整度，不能混為一談。

### 4.1 G1-c：ticker 差異的逐日歸因

| 日期 | 現象 | 歸因 | 比較是否有效 |
|---|---|---|---|
| 2026-08-12 | DB 既有精選 24 檔，但 **score 全為 NULL**（24/24 NULL） | **舊引擎產的**（當時 score 欄位未寫入） | 重建會算出 score → 不一致來自引擎版本，不是重建失敗 |
| 2026-09-21 | 缺 **3** 檔（3035／3711／4590）、多 **4** 檔（2882／6239／6425／6894）、**1** 檔 horizon 不同（1303） | **引擎版本漂移**（篩選／排序邏輯已改） | ticker 集合不可直接比，必須逐欄歸因 |
| 2026-08-13～08-19 | 當時根本沒有發佈精選（`market_screen_picks` stored=0） | 那些日子引擎整天 `continue`（沒有發佈日） | **比較無意義**：沒有可比對的對象 |

→ 這三類都屬於**引擎版本漂移／發佈日缺失**，不得記為「重建失敗」；
G1-a／G1-b 的 CLEAN 結果仍然成立（見第 3 節）。

母體 7 年成長 10.8%（1,862→2,063），每年 +1.5–2%。
**已知限制**：`daily_data2_full` 只含**現存**標的 → 已下市的股票不在任何一年的母體裡，

偏誤的量級無法從 DB 內部量化（缺的是「當年存在、現在已死」的名單），
只能揭露。實務影響：回測會系統性高估「買得掉」的假設。

小字說明：`_rebuild_picks.py` 新增的 `--no-truncation`／`--patch-date` 兩個旗標
**只是為了 G2 對照而加**：前者同時拿掉 `db.report_date(date)` context 與 `db.latest_date` patch（＝跑法 B），
後者只把 `latest_date` 釘到指定日（fallback 變體）。
**預設行為完全不變**——不給旗標時仍走原本的 `report_date` context ＋ `latest_date` patch 到目標日。
